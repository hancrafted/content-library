1. Sampler: one module for beat readings

Strongin-process
  • beat-means.pure.ts
  • factory-run.pure.ts (Aim.sampling, sampled)
  • factory-scenario.pure.ts (runAveraged)
  • factory-tour.pure.ts (readMean)
  • beat-means.pure.test.ts
BEFORE
createSampler({start,end,window,keys})
stepSampled(f,{k,n,s})
meanOf(keys, s.got)
FactoryRun.sampled → got
AFTER
Sampler.run(f, k, n) · .mean() · .readings
cursor and got private

Problem. Sampling {at, keys, got} is a bare record a caller creates empty and stepSampled mutates; progress is the implicit cursor s.at[s.got.length]. Three call sites hand-assemble it and apply meanOf(keys, got) themselves.

  • Tests hit one interface
  • Mutation stays internal
  • Judge and page share one object
  • Delete 3 caller recipes

BEFORE

AFTER

  • One pressure source, no stored copy
  • Delete a field and 2 writes
  • seed stops importing step
  • Stale press impossible

3. Trim the traffic Ctx

Worth exploringin-process
  • factory-traffic.pure.ts (Ctx)
  • factory-solve.pure.ts (context)
  • mechanics.pure.ts
BEFORE
Ctx.rework (unused)
Ctx.churn
Ctx.consts{inspect(unused),redo,keepExtra,maxBounces}
service: constOf(m.s,…)
AFTER
Drop the two dead fields now
then read redo/keepExtra/maxBounces as constOf(ctx.s, …) only if the 800-iteration solve stays as fast

Problem. Ctx pre-resolves strengths and constants into rework, churn and consts, while the step and service modules read the same mechanics through mechOf/constOf on Settings. Ctx.rework and Ctx.consts.inspect are read by nothing in the traffic pass (catchOf does it from ctx.s).

  • One way to read a mechanic
  • Ctx interface shrinks
  • Dead fields go
Pre-resolving is a defensible speed choice, so stop at the dead fields unless a timing check says otherwise.

4. One run start for judge and page

Worth exploringin-process
  • factory-scenario.pure.ts (scenarioStart)
  • factory-run.pure.ts (constructor, loaded, finishWarm)
  • factory-tour.pure.ts (startTour, backTour)
  • exchange-load.pure.ts
BEFORE
scenarioStart: settings, step 60, pile
FactoryRun: settings, chunk 60, pile
tour: passes startSettings again
AFTER
startOf(B, preset, seed, s?) returns {f, warmSteps, load()}
scenarioStart = startOf + step + load()
FactoryRun chunks the same warmSteps

Problem. The start protocol (startSettings, warm WARM_WEEKS unless clear, pile startBacklogOf) is written twice: once in scenarioStart as one step call, once in FactoryRun as chunks, and the tour passes startSettings that FactoryRun already defaults to. A change to how a state starts must be made in both, and only the characterisation pins would notice.

  • Locality: the start protocol in one place
  • Judge and page cannot diverge
  • Redundant s: arguments go
Touches FactoryRun, which the UI agent's scope uses; keep its public interface unchanged.

6. firstSpawn: keep, but name the carrier

Speculativein-process
  • first-spawn.pure.ts
  • factory-traffic.pure.ts
  • factory-service.pure.ts
  • factory-routing.pure.ts
  • factory-build.pure.ts
  • use-case-checks.pure.ts
BEFORE
5 callers: first = firstSpawn(…); sp === first
AFTER
Optionally add isCarrier(spawns, sp) beside it
keep firstSpawn

Problem. firstSpawn is spawns[0] behind a name; deleting it would spread the concept over five modules, so it passes the deletion test as a naming module. The real friction is that each caller then re-derives 'is this the carrying spawn' (sp === first).

  • Locality for the carrier rule
Low yield; the glossary term is the value. Do not delete.
