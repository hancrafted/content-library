One source of truth

1 Compute each beat’s steps once, or keep two copies?

Recommended A: the rule becomes structure.

EvidenceTwo-wayEffort: medium

What the principle means

A single source of truth (often called DRY, “don’t repeat yourself”) gives every fact or calculation one authoritative home. When two places each work it out, they agree only while someone remembers to edit both. The first missed edit is a silent bug, because both copies still run.

Where it comes from

Andy Hunt and Dave Thomas, The Pragmatic Programmer (1999): “Every piece of knowledge must have a single, unambiguous, authoritative representation within a system.” It is about knowledge, not about lines that merely look alike.

Why it helps here

The tour on the page and the headless judge must replay the same steps, or the judge proves nothing about what viewers see. Design-ADR 0024 §10 and §12 require this. Today one test enforces it after the fact; one plan makes it true by construction, and the test stays as a guard.

The code

  • Evidence aimAtStep (factory-tour.pure.ts:44) computes a beat’s end as t0k + stepsTo(st.run) and its sample start from the beat before.
  • Evidence playSteps (factory-scenario.pure.ts:51) and readBeats (:112) compute the same end and sample window for the judge.
  • Evidence Design-ADR 0024 §10/§12 requires the tour and the judge to read the same steps; today only the tour-equals-headless test enforces it.
  • Agent proposal One plan makes that agreement structural; the test stays as the guard.

A pure beatsOf(preset, t0k) in new factory-beats.pure.ts returns each beat’s settings, sample start, end step and keys. Files: factory-tour.pure.ts, factory-scenario.pure.ts, the new file with a sibling test (ARCH-003-sibling-tests). Characterisation pins and expect ranges stay unchanged; ecology:sim --seeds 10 must pass both scenarios after the commit.

Single source of truth Recommended

  • Tour and judge share one plan
  • Change a beat once
  • One new file

  • Copies can drift

One source of truth

2 Name use-case files in one place or two?

Recommended A: two adapters exist; they can drift.

EvidenceTwo-wayEffort: small

What the principle means

Ports and adapters (hexagonal architecture): the core defines a port, here the shape of a use case’s texts (data, English, German). Each environment brings an adapter that fills the shape from its own source. The page reads files baked in at build time; the CLI reads them from disk. The shape is the one fact; the adapters are plumbing.

Where it comes from

Alistair Cockburn, “Hexagonal architecture” (2005). The single-source-of-truth side of it is Hunt and Thomas, The Pragmatic Programmer (1999).

Why it helps here

One adapter behind a shape is a guess at a seam; two adapters are proof of a real one. Today both loaders build the same file names themselves, so a new words file must be added in two places or the CLI quietly misses it.

The code

  • Evidence use-case-data.ts:21 names each use case’s data, en and de files in SOURCES.
  • Evidence loadUseCase (ecology-sim.node.ts:50) builds the same file names itself and reads them from disk.
  • Agent proposal Two adapters behind one shape is a real seam, per the codebase-design rule “two adapters means a real one”.

One UseCaseTexts shape; the static-import adapter stays in use-case-data.ts, the file-read adapter in the CLI, and the file suffixes are named once. FE-007 §2.8 (the node entry) is unchanged: the CLI keeps its own .node.ts file.

Ports and adapters Recommended

  • One shape, two loaders
  • New file: one edit
  • Both loaders change

Leave it

  • No change
  • No work
  • Two lists to sync

Decoupling

4 Should the Slide use one entry point, or 13 internals?

Recommended A: it closes the silent-break path; hero can wait.

EvidenceTwo-wayEffort: mediumUnknown: painter copy unchecked

What the principle means

Low coupling through a narrow interface. A module that imports thirteen internals of another depends on every one of them, so any internal change can break it, often with no failing test in the owner’s own suite. A Facade offers one small entry point and keeps the rest private, which is information hiding.

Where it comes from

David Parnas, “On the Criteria to Be Used in Decomposing Systems into Modules” (1972) for information hiding; Stevens, Myers and Constantine, “Structured Design” (1974) for coupling; the Facade pattern in Gamma, Helm, Johnson and Vlissides, Design Patterns (1994).

Why it helps here

The Why · How · What Slide reaches into painter, layout and stage internals of the Explorable. A painter change can break the Slide while every Explorable test passes. With stillOf the Explorable owns the contract, and its own tests cover it.

The code

  • Evidence slides/why-how-what/factory-still-state.ts has 13 import lines, most into painter, layout and stage internals of the Explorable.
  • Unknown The review found it re-implements the painter’s document merging and rack slots; not re-checked line by line.
  • Evidence FE-007-explorable-pages allows Slides to import from src/explorables; FE-012-explorables §3 keeps routes and Episode metadata out of the Explorable, which stillOf does not touch.

stills.pure.ts in the Explorable returns FactoryStillState from stillOf(useCase, state, locale); the Slide imports only that. factory-still-state.test.ts moves next to it; software-ecology.test.ts stays. The hero preview (slides/hero/factory-preview.tsx) keeps its own card and slot geometry.

  • One new file

  • No second reader yet

Decoupling

5 Keep the tour’s stop point in the run?

Recommended A: stopping mid-frame needs the run’s step loop.

EvidenceTwo-wayEffort: A none, B/C large

What the principle means

Information hiding: keep a detail inside the one module that has to act on it, and keep everyone else ignorant of it. Moving the tour’s stop point out of the run would not delete it from the system; it would make the frame loop learn about tours, which spreads the knowledge and raises coupling.

Where it comes from

David Parnas, “On the Criteria to Be Used in Decomposing Systems into Modules” (1972). This recommendation goes against the architecture review’s proposal, which was made before the Sampler refactor (PR #551).

Why it helps here

“Stop at step k and sample on the way” is a primitive of the run’s own step loop; honouring it inside a frame’s step budget needs that loop. Revisit if a second, non-tour client ever needs to stop the run.

The code

  • Evidence The frame loop (use-factory.ts:141) calls run.advance(dt, speed) and knows nothing about tours; stepDue (factory-run.pure.ts:191) caps each frame’s steps at stopAt.
  • Evidence Only factory-tour.pure.ts and use-tour.ts:98 call run.aim; the page reads tour progress from the pure Tour value, not from the run.
  • Evidence The review’s smell (tour state on FactoryRun) was found before PR #551 took got and the cursor off it.
  • Agent proposal Moving the aim out (B or C) would make the frame loop carry tour state, which spreads it rather than concentrating it.

FactoryRun keeps aim, stopAt, arrived, sampled and sampledMean. Option B would make the frame loop drive a Tour module; option C would keep the aim in a React ref in use-factory.ts and pass it to advance.

Information hiding Recommended

  • No change
  • Loop stays tour-blind
  • Run keeps tour fields

Decorator: Tour wraps run

  • Tour drives the run
  • Run loses five members
  • Loop must know tours

Caller owns the aim

  • Loop passes the aim
  • Run holds no tour state
  • Loop gains tour state

Cohesion

6 Should start settings leave the dials file?

Recommended A: builders change with presets, dials with the model.

EvidenceTwo-wayEffort: small

What the principle means

Single responsibility: a module should have one reason to change. Behind it sits cohesion, how strongly a module’s parts belong together. High cohesion means one purpose, so a change touches one place and a reader finds it there.

Where it comes from

Robert C. Martin, Agile Software Development: Principles, Patterns, and Practices (2002); the cohesion idea comes from Stevens, Myers and Constantine, “Structured Design” (1974).

Why it helps here

The file mixes model tunables and dial lookup, which change when the model does, with Settings builders, which change when a preset or start changes. It also sits six lines under the 250-line lint cap, so the next edit forces a split anyway.

The code

  • Evidence factory-dials.pure.ts is 244 lines (cap 250) and holds tunables, dial lookup (dials, catches, pressureOf) and the builders (:167–244).
  • Agent proposal The builders change when a preset or start changes; the dials change when the model does. Two reasons, two modules.

idealSettings, realisticSettings, presetSettings, startSettings and custOf move to start-settings.pure.ts. The new file joins the MODEL and INTERNAL lists in factory-model-seam.test.ts; its sibling test takes the builder cases from factory-dials.pure.test.ts.

Single responsibility Recommended

Keep it simple

8 Share the start routine, or test it?

Recommended A: five lines are too small for a module.

EvidenceTwo-wayEffort: small

What the principle means

YAGNI and the wrong abstraction. Removing duplication pays only when the shared piece is deeper than what it replaces. A five-line module costs every reader a hop and gives them nothing back. A test that pins the two copies together buys the safety without the extra layer.

Where it comes from

Kent Beck, Extreme Programming Explained (1999) for YAGNI, “you aren’t gonna need it”; Sandi Metz, “The Wrong Abstraction” (2016): “duplication is far cheaper than the wrong abstraction”; John Ousterhout, A Philosophy of Software Design (2018) on shallow modules.

Why it helps here

Deletion test: removing a startOf would put back five lines in two callers, so it earns nothing. The risk that matters is drift between the page’s chunked warm-up and the judge’s one-shot warm-up, and an equivalence test catches exactly that.

The code

  • Evidence scenarioStart (factory-scenario.pure.ts:42) is five lines: create, return if clear, warm WARM_WEEKS, pile the start backlog.
  • Evidence FactoryRun (factory-run.pure.ts:72–84) does the same in chunks, because the page warms up over several frames.
  • Evidence backTour (factory-tour.pure.ts:113) passes s: startSettings(B, p), which FactoryRun already defaults to.
  • Agent proposal A shared module would be shallow; a test buys the same safety.

One equivalence test, and backTour drops its redundant startSettings argument. The test compares model state (weeks and a reading hash) after both starts, for a loaded and a clear preset, on two seeds.

Test, no new module Recommended

  • One test pins both starts
  • Drift gets caught
  • Five lines stay twice

DRY: shared routine

  • Both call one routine
  • Written once
  • Shallow extra layer

Leave it

  • No change
  • No work
  • Drift goes unnoticed

Keep it simple

9 A small helper, or a full entry module?

Recommended A: the order is consistent; a module repeats it.

EvidenceTwo-wayEffort: smallUnknown: file-load order

What the principle means

Extract Function, and YAGNI. When four handlers repeat the same two lines, name them once. A bigger module is worth it only when it removes complexity, not when it re-describes code that already runs in one order.

Where it comes from

Martin Fowler, Refactoring (1999), for Extract Function (first called Extract Method); Kent Beck, Extreme Programming Explained (1999), for YAGNI.

Why it helps here

Option B’s gain, one order for every entry, already holds today. Its cost is a new pure module, a hook and a split of Parts. FE-001 transient state and FE-012 §4.1 (the parent owns state) hold either way.

The code

  • Evidence onPreset, onTour, onReset and onUseCase (software-ecology.client.tsx:168–186, reset-state.ts:37) each run: dismiss, show(viewOf(B, id)), apply(B, id), then their own act.
  • Evidence Their own acts differ: setPreset, tour.start, controls.reset(defaults), setUseCase.
  • Unknown Whether file load (loadInto, use-exchange-wiring.ts:58) runs the same order was not checked line by line.
  • Agent proposal A pure enterState would be a second description of what the handlers already do.

Option A names the shared pair enter(bundle, id) inside useHandlers; each handler loses two repeated lines, and Parts and the hooks stay. Option B adds a pure enterState(B, id) returning view, compare, display and settings, plus a useEnterState hook.

  • Handlers call one enter()
  • Repeated lines vanish
  • Little else improves

Intent-driven module

  • One described path
  • New module and hook

Keep it simple

10 Delete two unused fields, or restructure?

Recommended A: B needs a benchmark for little gain.

EvidenceTwo-wayEffort: tinyUnknown: speed cost of B

What the principle means

Remove dead code. Code nobody reads still costs everyone who reads past it. Deleting it is the cheapest simplification there is, because behaviour cannot change. Restructuring live code is a different bet: it needs proof that it pays.

Where it comes from

Martin Fowler, Refactoring (1999), counts dead code among the smells; Kent Beck, Extreme Programming Explained (1999), gives the YAGNI rule behind it.

Why it helps here

The solve runs up to 800 passes, and the precomputed constants avoid a lookup inside that loop. Dropping them (option B) would need a before-and-after benchmark, which is not worth it for one fewer field group.

The code

  • Evidence Ctx (factory-traffic.pure.ts:47–67): no non-test code reads ctx.rework or consts.inspect (grep, this session).
  • Evidence The solve runs up to 800 passes; the precomputed consts avoid a lookup in that loop.
  • Unknown How much speed reading constOf in the loop would cost: not measured.

Delete rework and consts.inspect and their setup lines; keep consts: { redo, keepExtra, maxBounces }. Speed and output stay the same.

  • Free and safe
  • Nothing else improves
