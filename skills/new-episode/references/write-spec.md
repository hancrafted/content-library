# write-spec

Output: `docs/episodes/<slug>/spec/spec.html`, the **Spec**: one static HTML page showing the Title slide with three **Options**, each a set with every section slide, then every page Slide with two or three Options under its title, Visual idea, Voice script and Speaker notes ([design-ADR-0011](../../../docs/adr/0011-episode-design-is-reviewed-as-a-static-html-spec.md)). [The sample](../assets/sample-episode/spec/spec.html) shows its shape; [the Spec calibration](spec-calibration.md) holds what every Spec shares (the render presets, the template's slots, the save API and the Next actions); `src/pipeline/lib/episode-spec.pure.ts` holds its contract and the staging test enforces it. The job runs in the orchestrator session, because it spawns the designers, and ends at the Spec Gate: The user reviews the page, a Slide they set to Redesign is redesigned, and they approve once every Slide has one pick.

## Prompt

Name every domain concept by its [`GLOSSARY.md`](../../../GLOSSARY.md) term, never an _Avoid_ word. Before the Gate the Dossier is the draft the Spec is written from; from the Gate on the Spec is the Episode's only source.

1. **Visual language first.** Read the Brief's `## Style` line and the matching named style in [the design guide](../../../docs/design/design-guide.md), then write the `Visual language` card's markup to `.scratch/<slug>/spec/visual-language.html`: the Episode's recurring motifs, its motion character and how it uses the accent colours, in a few lines, narrowing the Style and never contradicting it. The page's `Style` card is the Brief's line, which the assembler copies.
2. **One designer per Section and one for the Title slide, in parallel.** Spawn the Title-slide designer by [`spec-designer.md`](spec-designer.md#the-title-slide-designer), told the Brief's Red thread and the Sections with their section slides' Voice scripts; it returns three Options, each a **Hero motif** drawn from the Red thread and shown as a set: the Title slide that sets it and one section slide per Section that echoes it and brings in that Section. Spawn one subagent per Dossier h2, each told to use the `ui-ux-pro-max:slides` skill and to follow [`spec-designer.md`](spec-designer.md), `model` the agent's `model`, with the Visual language, its Section's Slides by Dossier anchor and number, its fragment file `.scratch/<slug>/spec/<section-slug>.html`, and the command `npm run episode:spec-preview -- <its fragment file>`, which renders the fragment in the Spec template's frame, checks the Spec contract and exits 1 on any violation: a designer returns only on exit 0. Each returns, per Slide, two or three Options as markup fragments: the mock, the figcaption and the build notes, the recommended one named. Designers return fragments; you alone run the assembler, since parallel edits to one file conflict.
3. **Assemble the page.** Write the `Episode page` card's markup to `.scratch/<slug>/spec/episode-page.html`: it is `implement-episode-init`'s part, the route (`/guides/<slug>/` and the Guide record for a Brief whose Format is `guide`, by [A Guide](implement-episode-init.md#a-guide)), the metadata from the Brief, the registration, the Title slide (the picked Title-slide Option, built as the record's `title` Slide; its Voice script included, which the kit gives no own slot: map the h1's paragraphs to the first segment of the first section slide), one placement marker per Section by the name [`implement-episode-init.md`](implement-episode-init.md#placement-markers) gives, and post-build step 8 of [episode-migration](../../../docs/features/episode-migration.md): capture `tests/post-build/episode-text/<ep>.{en,de}.json` with `npm run build` then `npm run test:build`; the slug joins `PUBLISHED_SLUGS` only at publication. Then run `npm run episode:spec-assemble -- <slug>`. It reads the Brief, the Dossier, every fragment in `.scratch/<slug>/spec/`, `visual-language.html`, `episode-page.html` and every feedback round, and writes `docs/episodes/<slug>/spec/spec.html`. It fills `assets/spec-template.html` as [the Spec calibration](spec-calibration.md#template-and-slots) lays out: the slots, the attributes it sets and the markup it builds itself. The word tabs carry the Dossier's words copied word for word: from the Gate on they have no other home. It also writes the meta block and the `data-picked` and `checked` locks of every round. It renders what exists (Brief: Slide cards with purpose and visual idea; plus Dossier: Voice script and Speaker notes; plus fragments: Options), runs the Spec contract once Options exist and exits 1 on any finding, and refuses once the Spec is approved. [The sample](../assets/sample-episode/spec/spec.html) shows the page it builds. Never edit `spec.html`: change a fragment or a card file and assemble again.
   - Before the reviewer, look at the served page, one Slide per Section: `npm run inspect-page -- --url http://127.0.0.1:<spec port>/ --clip '#<slide slug>' --width 1440`, on the port `npm run episode:spec -- <slug>` printed. The designers' `.preview/*.png` screenshots do not count: each compiles its own `design.css`, so a mock can look right there and broken on the page the user reviews. A mock that renders as a title over empty shapes goes back to its designer before any reviewer sees it. Tell the reviewer the served URL: it judges that page with `inspect-page` as well, never the `spec-preview` render alone, since a Spec can pass there and still show broken UI to the user.
4. **A failed rubric line goes back to that Section's designer only**, quoted verbatim; the other Sections stay as they are.

### What the designers read

[`spec-designer.md`](spec-designer.md) lists it, with the fidelity bar a mock meets and the markup rules. A `no-library-match` note is input for the designer. Point each designer at the files; never paste them.

### What an Option settles

An Option settles the on-screen title, the layout, the visual components, shapes, graphs and charts, the hard UI calls (hierarchy, density, emphasis) and hover. Build settles the rest: dark mode, mobile width, German, final body copy and exact spacing. Mocks are desktop width, light theme and English, styled with token classes only, so `design.css`, compiled from `globals.css`, renders them as the site will. A mock is the finished Slide at rest, drawn at full fidelity: real content, a composition with one focal point, the Style's material, and inline SVG for every arrow, curve and chart ([`spec-designer.md`](spec-designer.md#the-mock-is-the-slide)). The user picks from the mock alone, so a wireframe gives them nothing to pick.

- **Slide header.** A page Slide's mock shows the shared Slide header the wrapper renders above its Scene: the Eyebrow (its Section title and `n / N`), the title and the caption. The Eyebrow is computed, so the build notes give no key for it; the Scene they describe holds the visual alone.
- **Hover is live.** Where hover helps the user point at the Slide while they present, the mock uses the shared hover classes from `globals.css` (`card-hover--raise`, `card-hover--outline`, `focus-group--dim-others` with its `focus-group__item`s, `hover-reveal__detail`, each beside its block class), so the user reviews it in the preview; the build notes name them.
- **Context markers.** Every fact on a Slide whose Speaker note carries a source shows a Context marker beside it in the mock, the speech-bubble icon the site builds as `ContextMarker`: in text, after the phrase in parentheses, `… keeps nothing between requests (💬)`; on a card, column or chart, in its corner or beside its label. In the mock it is `<span data-spec="context-marker" data-note="<Speaker note title>" role="img" aria-label="Speaker note: <title>">` around a small inline SVG bubble in token classes, and the build notes name the Speaker note each marker opens. The staging test refuses a marker whose `data-note` is no Speaker note title of its Slide.
- **Entrance is shared.** The wrapper's play-once entrance types the header in and fades the Scene up, so no Option or build note specifies entrance motion. A `motion:` note covers purposeful emphasis or hover alone, and a mock shows such motion at its end state.

The Options of one Slide are **true alternatives**: they differ in layout, visual metaphor or chart type. Creative freedom holds inside the context above and the ADRs:

- The figcaption gives the Option's id, its reason in one line and its build cost: Slide library entry used as is, Master slide copy, or Scene. A Title-slide Option's build cost covers the set: the record's `title` Slide and a Scene per section slide.
- The build notes say whether the Dossier's `master:` and `motion:` are kept or overruled, an overruled one with its reason, and name the parts, tokens, props and i18n keys, so the mock maps onto the code.
- A Slide copies a Master slide with changes, or is a one-off Scene from `SlideFrame` and the kit's `<Title>` (FE-002 §3). A new part or motion lives in the Slide's own folder, a server part or its own `*.client.tsx`, and moves to `slide-shared/` once a second Slide needs it (FE-007).
- A Slide is a scrolling web section, not a fixed frame (FE-009): the wrapper's "at least viewport height" is the only height rule.
- An Option that redraws a design reference page names it in its build notes by repo path, `Design reference: docs/episodes/<slug>/reference/<file-slug>/pages/page-<NN>.jpg`, then `Build against this page: keep <what>; change <what>`.

### Settle it as a Scene

Run 1's designers stopped, or handed the question to the user, whenever the library had no part that fit. Those answers are the worked examples of what to settle instead, in the `Design answer` bullets of the run-1 tickets [#100](https://github.com/hancrafted/content-library/issues/100), [#101](https://github.com/hancrafted/content-library/issues/101), [#102](https://github.com/hancrafted/content-library/issues/102) and [#103](https://github.com/hancrafted/content-library/issues/103). Each begins from "No catalog part carries it" or "the catalog has no match" (run 1's word for the Slide library), then ends in an `Open for the user` question. That question is the designer's to settle as Options: a Scene from the frame parts is allowed (FE-002 §3), so the Options choose and give their reasons. Read those four tickets with `gh issue view` before designing a Slide the library does not carry.

## The Spec Gate

The Job span stays open from the first Attempt to the approval; each review round is a Gate span on the Run, so waiting time stays apart from working time.

1. **Draft.** After the Attempt passes (job loop steps 1 to 6), commit the page through the `commit` skill with `Gate: draft spec-<n>`, `<n>` the review round from 1, then `open-gate write-spec "draft spec-<n>"` and stop. In round 1's stop message, quote every `spine-change` note of the `write-dossier` Job, so the user judges each change to their spine first. Tell the user to run `npm run episode:spec -- <slug>`: it serves the Spec on a free port from 4000. The page is self-contained (`spec-assemble` inlines its CSS; no external file, script or link), so a page built before that runs once through `node skills/new-episode/scripts/spec-inline.ts <spec.html>`. Each Slide starts on its recommended Option; they change a pick, set a Slide to Redesign, dictate a note where one helps and save. The save writes the next `feedback/<NN>/feedback.md`, `via: spec`, in the line format of [the Spec calibration](spec-calibration.md#saving-the-review): an item for the Title slide and one per page Slide naming their picks (`none` for Redesign), then the notes and the Next action. A pasted Copy as prompt block is the same round: write its lines under the frontmatter and `# Feedback round <N>` of the saved rounds (`via: spec`, `<N>` from its lead line) to `feedback/<NN>/feedback.md`, then go on from step 2.
2. **Read the round.** Commit the feedback file through the `commit` skill, then `score "gate:draft spec-<n>" gate changes --source human:han --via commit --comment "<the round's file>"` and `close-gate "draft spec-<n>"`. Treat the `page` note as an Episode-wide change request, applied in step 3 alongside the Slides' notes.
3. **Lock.** Fold each locked Slide's note into its Option's build notes in the fragment file, and the Visual language note into `visual-language.html`, then run `episode:spec-assemble`: it marks each Slide with exactly one pick, the Title slide included, `data-picked` and ticks its checkbox, so the next round comes ticked and needs nothing on that Slide. A Slide left on its recommendation is locked like any other pick. When a note renames a concept, apply it to `brief.md`, `dossier.md`, `title.html` and every fragment, then run `episode:spec-assemble -- <slug> --forbid <old term,old term>`: it exits 1 naming file and line while an old term survives in the staging folder.
4. **Redesign.** Run step 4 when the round's `next` line says `redesign`, and step 5 when it says `approve`, without asking in chat; a round with no `next` line (a form saved before it existed) is the one case to ask. When a Slide is set to Redesign (`picked: none`) or has several picks, `begin-attempt write-spec` and spawn designers for those Slides only (the Title-slide designer for `top`), each given its note and picks: Redesign is "none fit, try what the note says", or fresh Options when it has no note, several is "combine these". Replace those Slides' Options, lettered from `a` again, and leave every locked Slide as it is. Run the checks and a fresh reviewer on the redesigned Slides, then `end-attempt write-spec ok` and go to step 1 with `<n> + 1`.
   - **Prototype loop.** When the user asks to iterate an interactive Explorable Option on its own, take it out of the round:
     1. Extract the Option into one self-contained `.scratch/<slug>/prototype/flow.html`, serve that folder, and keep a single designer addressable for every round.
     2. Save each note verbatim as `feedback-<NN>.md` beside the prototype; the designer reads it as the spec.
     3. When a note changes the model or the files, grill the user on it, then rewrite the Explorable's design-ADR and feature guide (and the Brief when its Analogy moves) before the next prototype round.
     4. _Done when_ the user calls the prototype converged. Fold it back into the Section's fragment as that Slide's Options, then go on from step 4's checks and reviewer.
5. **Approve.** When every Slide has one pick, tell the user the Spec is theirs to approve. They run `node skills/new-episode/scripts/approve.ts docs/episodes/<slug>/spec/spec.html`, which appends their `verified` entry to the meta block, and the same commit deletes `dossier.md`: `git rm docs/episodes/<slug>/dossier.md`, committed with `Gate: approved spec`. An approved Spec beside a Dossier, or with a Slide not picked exactly once, fails the staging test.
6. **Close.** `end-job write-spec ok`, then log one Score on the Job, derived from the rounds: `episode:run -- <slug> score write-spec gate "<outcome>" --source human:han --via commit --comment "<rounds> rounds"`. The outcome is `approved as drafted` (one round, every pick the recommended Option, no note), `approved after edits` (a pick off the recommended Option, a note folded in, or a later round) or `approved unreviewed` (approved without a saved round). When most runs are `approved as drafted` (`SELECT value, count(*) FROM scores WHERE name = 'gate' AND source = 'human:han' GROUP BY value`; `approved unreviewed` counts for nothing), the Gate's rounds shrink to a glance.

## Done when

The job's `checks:` in `assets/pipeline.yml` run by the check table in [SKILL.md](../SKILL.md#the-job-loop) on every Attempt, and the Spec Gate's step 6 has run: the Spec is approved with exactly one picked Option per Slide, `dossier.md` is gone, and the Job carries its gate Score. The Build jobs then build from the Spec alone.

## Rubric

1. Every page Slide carries two or three Options and the Title slide three, true alternatives: Options that differ only in colour, spacing or copy fail.
2. Every Option follows the Spec's Visual language, inside the Brief's Style.
3. Every Option's figcaption gives a one-line reason and its build cost, and its build notes name parts, tokens, props and i18n keys.
4. Every overruled `master:` or `motion:` names its reason.
5. Colour, size and weight are tokens (FE-011); every import the build notes imply is one FE-007 §5 allows.
6. Every Option follows FE-009: no fixed height, no clipping, Foreground clear of the chrome.
7. Every Option that redraws a design reference page names its page image by repo path with `Design reference:`, and says what to keep and what to change.
8. No Option asks the user a design question it could settle as a Scene; it chooses and gives its reason.
9. The recommended Option is the one the designer would build, and its reason says why over the others.
10. Every mock, rendered at 1440px, draws the whole Slide with its real content (title, every note, label, number and arrow) at full fidelity; a mock showing a title over empty shapes, grey boxes or a paragraph fails.
11. Every Title-slide Option is a Hero motif drawn from the Red thread: its Title slide sets it, and each section slide echoes it and brings in its own Section, so the set foreshadows the Episode.
12. Every mock that has a point to show on hover uses the shared hover classes, and no Option or build note specifies entrance motion.
13. Every fact a Slide shows whose Speaker note carries a source has a Context marker beside it in every Option's mock, and the build notes name the note each marker opens.
14. Every Slide draws one client industry, so its examples, labels and figures belong to the same industry.
15. No Slide, Option or Speaker note addresses the viewer with "your turn" or an equivalent hand-over.
16. Note tints carry meaning: cash, cost and revenue each keep one tint, used for that meaning in every Option and Slide.
