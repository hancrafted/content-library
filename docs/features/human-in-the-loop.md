# Human-in-the-loop Shared visual

Read before placing, changing or testing the human-in-the-loop Shared visual (`src/components/slide-shared/human-in-the-loop/`). To write a Workflow file, read [agentic-workflow.md](agentic-workflow.md). Binding rules: [FE-012 Shared Visual Content](../../.archgate/adrs/FE-012-shared-visual-content.md), [FE-006](../../.archgate/adrs/FE-006-server-client-boundary.md) §5, [FE-007](../../.archgate/adrs/FE-007-module-layering.md) §5 and [FE-011](../../.archgate/adrs/FE-011-design-tokens.md). This guide holds the detail that does not bind. A **Workflow** is defined in the [glossary](../../GLOSSARY.md).

## Placing it

A Slide renders `<HumanInTheLoop workflow="summer-party" locale={locale} diagram={…} />` from `human-in-the-loop.tsx`, the server entry. It reads the Workflows and the words of the locale at build time and hands them, serializable, to the one client parent `human-in-the-loop.client.tsx`.

- `words={{ ui }}` overrides the chrome words key by key. A Workflow has no words to override: its file is written in one language and renders as written.
- `diagram` carries the Slide's own markers, popovers, notes (`target`), gate words and the worked-chat button, keyed by stage and job id. Its `initials` draws each stage's BRIEF letters as circled capitals (English letters in German too, with German tooltips); a Slide that leaves the acronym unnamed says `initials: false`. The ai-attention-span Slide sets `initials: false` on purpose: the BRIEF acronym is shown only in the freelancer Episode (onboard-ai-every-time). `jobsLabel` is a template (`{stage}: jobs`) for every stage's list of jobs, `gateLabel` on a stage slot is the word for its gate, and a stage's or job's `popover` carries no title: the diagram titles it with the stage name. The sign-off card is the Workflow's (`card` on the stage), never a Slide's.
- `level`, `readonly` and `controls` set the start state. `readonly: true` makes no column a button and hides the Technical toggle, so the Slide shows the diagram alone. `controls` is the Preset's override of the typed control registry in `toolbar-controls.pure.ts` (`picker`, `level`, `download`, `upload`), laid over it key by key, e.g. `{ picker: { show: false } }`.
- One pill toolbar, mirrored from the Context visual's (`human-in-the-loop.module.css`; FE-007 §5 bars a client leaf from importing the Context folder, so the tokens are copied, not imported): the use case picker ("Use case:" and a native select of the Workflows), a separator, then icon buttons for Technical (`</>`), download and upload. One tooltip (`tip.client.tsx`) serves the toolbar icons, the BRIEF circles, the section purpose markers and the modal header; the prompt row's buttons have their words written on them and no tooltip. The tooltip shows on hover and keyboard focus, is hoverable, and Escape dismisses it before it reaches the dialog (WCAG 1.4.13); the controls keep their own `aria-label`, never `title`. The icon buttons are 36px (`size-9`), the same as the Context toolbar's 2.25rem; the BRIEF circles are 24px with a gap (WCAG 2.5.8). There is no Watch / Try switch: every stage column is one button that opens the stage's modal; on hover or keyboard focus its "Practice it" face rises into the foot of the column (always shown where nothing hovers). Below a 672px Scene the stages stack; above it they stand in one row of columns at least 11rem wide, which scrolls sideways when they do not fit.
- The diagram has a `view` (`presentation | detailed | handson`), independent of `level`, held by the parent and never stored: a reload returns to the Preset's `view` (default `presentation`). Hide the view control with `controls={{ view: { show: false } }}`. The Presentation view (`diagram-presentation.tsx`, cards in `stage-card.tsx`) draws one card per stage: title, `summary`, a labelled "checked" mark where a job is reviewed, the gate badge. A repeated stage (`foreach`) is one branch card per round with a fan out before and a fan in after (`diagram-layout.pure.ts`; branches = the run model's rounds, else the teaching cap); a gated stage has a dashed "send back" arc under it, which becomes "send back" on the gate badge where the stages stack. The Detailed view (`diagram-detailed.tsx`, cards in `job-card.tsx`) draws the same columns, each stage card holding its jobs as job cards in `needs` order (`workflow-order.pure.ts`) joined by arrows, each with its summary and the labelled check mark; a repeated stage is drawn once, its jobs inside a dashed bracket labelled "× each round (n)" (the run's rounds, else the teaching cap). A job card is a button (`job-button.client.tsx`, `data-try` and `data-try-job`) that opens the stage's modal at that job; a readonly Preset has none. The Hands-on view is the Detailed layout (the same `diagram-detailed.tsx`) with the viewer's run laid over it, read only from the run model (`DiagramProps.run`): each job card says open, done or checked with an icon and a word, each stage shows its count ("3/5"), and a repeated stage's bracket holds the rounds the run has, titled by the pasted H3s (at most the teaching cap in teaching mode; no rounds yet: the stage's jobs once, open). A review step in the popover has an "I checked this result" box that writes `stage.job.checked` (`#k` per round), which is what turns a job from done to checked. The Slide's `diagram.jobs` slots (`popover`, `detail`, `marker`, `after`) are read by the Detailed view only, so a Slide that uses them sets `view="detailed"` (brief-the-venue and ai-attention-span do); Presentation reads only the stage slots.
- Naming against FE-012 §4.3: the ADR's `renderMode` is `level` here, one global value. There is no per-part override because no part has a Simple and a Technical view of its own; the Level changes only what a step copies.

## Parts

The parent owns all state (`workflow-state.pure.ts`), computes `workflowView` once per change and gives each part its slice: `toolbar-part`, `diagram-part`, `modal-part`. The modal is one information architecture for every stage: the title `<Stage>: Practice it` with the learning goal under it, the simple/technical toggle and an X (Esc and the backdrop close too); on a wide screen the tasks as numbered Do and Review steps on the left and the details of the task in focus on the right (why it matters, the example result, what good looks like), on a phone one full-screen column with the details folded under each task. Each step is a `TryPrompt` (`core-components/try-prompt/`), the modal's first one open and the rest collapsed, with paste-in slots, a marker per section purpose and, left to right, "Copy prompt" (a tick and "Copied" confirm it) and "Open in ChatGPT", which opens an empty chat in a new tab: the link never carries the prompt, since a long prompt breaks a prefilled one. A repeated stage (`foreach`) shows one stepper item per round in Simple, titled by the H3 the viewer pasted (the example's H3 before that), and one orchestrator prompt in Technical. What the stepper and the toolbar say about progress comes from the run model, `workflow-run.pure.ts`: job states, rounds, per-stage counts, the teaching lock and the translation between result keys (`stage.job`, `stage.job#k`) and prompt markers. FE-012 §4.5 asks for a pure `*-view.tsx` where a part can render alone; the diagram, its job cards and the modal compose client leaves and are only ever shown by a client part, so they stay plain `.tsx`. Every handoff is a markdown document drawn by the one generic renderer (`markdown-view.tsx`). The glyphs the visual draws live in `slide-shared/glyphs/`.

## Saved progress

A run (the pasted results and the teaching flag) is saved in the browser under the second storage key, `hancrafted:progress` ([FE-001](../../.archgate/adrs/FE-001-state-management.md) §3). One entry per authored Workflow, `human-in-the-loop/<workflow id>`, carrying `hash`, `teaching` and `results`, so every Episode and both languages share one run. The hash is a sha256 of the English and German files together (`hashFor` in `workflow-data.ts`, built at build time by `src/lib/pair-hash.pure.ts`). Reading and writing go only through `src/lib/prefs-storage.ts` (`readProgress`, `writeProgress`, `removeProgress`); the hook `src/hooks/use-progress.ts` loads in an effect, so the static page never depends on storage, and saves on change. A stored entry of another hash never loads: a fresh run starts, saving pauses, and a note offers "Download old progress" or "Discard"; the old entry stays until the viewer chooses. A refused write (quota, private mode) shows a note asking for a download. An uploaded Workflow is not saved. The run model (`workflow-run.pure.ts`) stays the one place that reads results; storage persists its inputs and never forks it.

## Adding a Workflow

A Workflow is one YAML file per language; what is written renders as written. The authoring guide is [agentic-workflow.md](agentic-workflow.md): the schema, markers, slots, repeated stages, handoff templates and every loader problem. Start from `summer-party.en.yml` and `summer-party.de.yml`.

1. Register the pair in `workflow-data.ts` (`FILES`, `WORKFLOW_IDS`). `workflow-pair.test.ts` holds both files to one structure (FE-012 §1.3), and the loader checks every sample and example against its template. The build throws each problem of a shipped file.
2. Viewers may also upload a Workflow file (the same shape, in any language); problems are listed under the toolbar and the authored Workflow stays. A download writes the current file as it is; pasted values are not exported.

## Testing

- Fast suite: `*.pure.test.ts` and `*.test.ts` beside the files (Workflow loading, the pair structure, view model, state, markdown handoffs).
- Browser seam: `human-in-the-loop.browser.test.ts`, local only (`npm run test:browser`), drives the Slides Episode's "Human in the loop" Slide in the shared headless Chrome: the pill toolbar, a stage's Try it modal (title with learning goal, the simple/technical toggle and X, two columns on desktop with the details following the focused task, full screen on a phone with the details folded under each task, Chat 1..N tabs and the Technical orchestrator, "Open in" written out or icon only, collapsed prompts, copy, chat links, "Copied", backdrop, X and Escape close), Compare's one multiple research slot with its three samples, one example per Research chat, every stage of both Workflows in English and in German (`/de/episodes/slides/`) with no unfilled marker, Vacation with its own card lines, a broken and a valid upload, axe in light and dark, and phone width. `HITL_URL` names the page (default `http://localhost:3000/episodes/slides/`), served by `next dev` or `npm run preview`.
- Episode text captures (`tests/…/episode-text`) include the toolbar words; recapture them when a word changes.

## Progress file

"Save progress to a file" (toolbar, `progressDownload`) and the "Download progress" notes write one YAML file, `<workflow id>-progress.yml`: `workflow`, `hash`, `teaching` and `results`, every result a block scalar so a pasted Markdown result reads as it is (`progressFile` in `src/lib/progress.pure.ts`). "Load progress from a file" (`progressUpload`) reads it back with `readProgressFile`: a file that is no progress file, that names another Workflow, or whose hash is not the shown Workflow's is refused with a message naming the Workflow (`refuse*` words), and the run stays as it was. "Upload your own Workflow" (`upload`) is a separate, second action. An uploaded Workflow has no saved run, no hash to vouch for a file, and so neither progress action; the toolbar shows them only for an authored Workflow.
