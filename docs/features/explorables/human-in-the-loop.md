# Human-in-the-loop Explorable explanation

Read before placing, changing or testing the human-in-the-loop Explorable explanation (`src/explorables/human-in-the-loop/`). To write a Workflow file, read [agentic-workflow.md](agentic-workflow.md). Binding rules: [FE-012 Explorable Explanation Content](../../../.archgate/adrs/FE-012-explorable-explanation-content.md), [FE-006](../../../.archgate/adrs/FE-006-server-client-boundary.md) §5, [FE-007](../../../.archgate/adrs/FE-007-module-layering.md) §5 and [FE-011](../../../.archgate/adrs/FE-011-design-tokens.md). This guide holds the detail that does not bind. A **Workflow** is defined in the [glossary](../../../GLOSSARY.md).

## Placing it

A Slide renders `<HumanInTheLoop workflow="project-plan" locale={locale} diagram={…} />` from `human-in-the-loop.tsx`, the server entry. It reads the Workflows and the words of the locale at build time and hands them, serializable, to the one client parent `human-in-the-loop.client.tsx`.

- `words={{ ui }}` overrides the chrome words key by key. A Workflow has no words to override: its file is written in one language and renders as written.
- `diagram` carries the Slide's own markers, popovers, notes (`target`), gate words and the worked-chat button, keyed by stage and job id. Its `initials` draws each stage's BRIEF letters as circled capitals (English letters in German too, with German tooltips); a Slide that leaves the acronym unnamed says `initials: false`. The ai-attention-span Slide sets `initials: false` on purpose: the BRIEF acronym is shown only in the freelancer Episode (onboard-ai-every-time). `jobsLabel` is a template (`{stage}: jobs`) for every stage's list of jobs, `gateLabel` on a stage slot is the word for its gate, and a stage's or job's `popover` carries no title: the diagram titles it with the stage name. The sign-off card is the Workflow's (`card` on the stage), never a Slide's.
- `level`, `readonly` and `controls` set the start state. `readonly: true` makes no column a button and hides the `</>` toggle, Demo mode, Debug and Reset and never shows progress, so the Slide shows the diagram alone. `controls` is the Preset's override of the typed control registry in `toolbar-controls.pure.ts` (`picker`, `view`, `level`, `demo`, `debug`, `progressDownload`, `progressUpload`, `download`, `upload`, `reset`), laid over it key by key, e.g. `{ picker: { show: false } }`.
- One pill toolbar, in this order: the use case picker (a shadcn `Select`, "Use case:"; each option is the Workflow's title with its optional top-level `description` under it in muted text, the closed trigger shows the title only), a separator, then Stages · Jobs, the `</>` toggle (lucide `Code`; off is Chat, the default, on is CLI which shows the one-time setup and the `/skill` commands; `data-control="level"`, `toggledLevel` in `level-toggle.pure.ts`), Demo mode, the Debug toggle (lucide `Bug`, default off, only in development or with `?debug`), Save · Load progress, Download · Upload Workflow; Reset stands apart after the pill. Save progress and Reset show only once the run has work (the `hasWork` that colours Reset); Load progress always shows, so a new device can restore a run. The popover's toolbar uses the same `</>` toggle and Demo mode. One tooltip serves every icon; the controls keep their own `aria-label`. The icon buttons are 36px (`size-9`). There is no Watch / Try switch: every stage column is one button that opens the stage's modal; on hover or keyboard focus its "Practice it" face rises into the foot of the column. Below a 672px Scene the stages stack; above it they stand in one row of columns at least 11rem wide, which scrolls sideways when they do not fit.
- The diagram has a `view` (`stages | jobs`), independent of `level`, held by the parent and never stored: a reload returns to the Preset's `view` (default `stages`). Stages is the high-level view, one card per stage; Jobs is the detailed view, every job of each stage. Hide the view control with `controls={{ view: { show: false } }}`. Hands-on is not a view: once the run has work (and the Preset is not `readonly`) the parent hands the diagram the run (`DiagramProps.run`, read only from the run model) and both views show it; with no work, or `readonly`, they are plain. The Stages view (`diagram-stages.tsx`, cards in `stage-card.tsx`) draws one card per stage: title, `summary`, a labelled "checked" mark where a job is reviewed, the gate badge. With a run, each card instead says its count ("2/3") and its open, done or checked state (`state-mark.tsx`), and a repeated stage's round cards take the pasted H3 titles with their own state. Cards stand at the top of their column. A repeated stage (`foreach`) is its name on top, then one branch card per round, then its summary, with a fan out before and a fan in after (`diagram-layout.pure.ts`; branches = the run model's rounds, else the demo cap); every hairline is measured from the column's top. The Jobs view (`diagram-jobs.tsx`, cards in `job-card.tsx`) draws the same columns, each stage card holding its jobs as job cards in `needs` order (`workflow-order.pure.ts`) joined by arrows; a repeated stage is drawn once, its jobs inside a dashed bracket labelled "x each <item> (n)" (`<item>` is the stage's `foreach.item`, else "round"; n is the run's rounds, else the demo cap). With a run, every job card says open, done or checked with an icon and a word, each stage shows its count, and the bracket holds the rounds the run has, titled by the pasted H3s (at most the demo cap in Demo mode; no rounds yet: the stage's jobs once, open). A job card is a button (`job-button.client.tsx`, `data-try`, `data-try-job` and, inside a round, `data-try-round`) that opens the stage's modal at that job and round; a readonly Preset has none. A review step in the popover has an "I checked this result" box that writes `stage.job.checked` (`#k` per round), which turns a job from done to checked. The Slide's `diagram.jobs` slots (`popover`, `detail`, `marker`, `after`) are read by the Jobs view only, so a Slide that uses them sets `view="jobs"` (brief-the-venue and ai-attention-span do); Stages reads only the stage slots.
- Naming against FE-012 §4.3: the ADR's `renderMode` is `level` here, one global value. There is no per-part override because no part has a Simple and a Technical view of its own; the Level changes only what a step copies.

## Parts

The parent owns all state (`workflow-state.pure.ts`), computes `workflowView` once per change and gives each part its slice: `toolbar-part`, `diagram-part`, `modal-part`. The modal is one information architecture for every stage: the title `<Stage>: Practice it` with the learning goal under it, the simple/technical toggle and an X (Esc and the backdrop close too); on a wide screen the tasks as numbered Do and Review steps on the left and the details of the task in focus on the right (why it matters, the example result, what good looks like), on a phone one full-screen column with the details folded under each task. Each step is a `TryPrompt` (`core-components/try-prompt/`), the modal's first one open and the rest collapsed, with paste-in slots, a marker per section purpose and, left to right, "Copy prompt" (a tick and "Copied" confirm it) and a shadcn button group of AI chats, "ChatGPT | Gemini" (`chat-buttons.tsx`), each with its mark and a tooltip, shaped like Copy prompt (the mark alone on a phone), opening an empty chat in a new tab: a link never carries the prompt, since a long prompt breaks a prefilled one. The buttons are `ui.openAIButtons` in the config pair, unless the job names its own `openAIButtons` (a page job names Gemini alone; `docs/features/agentic-workflow.md`). A repeated stage (`foreach`) shows one stepper item per round in Simple, titled by the H3 the viewer pasted (the example's H3 before that), and one orchestrator prompt in Technical. What the stepper and the toolbar say about progress comes from the run model, `workflow-run.pure.ts`: job states, rounds, per-stage counts, the demo lock and the translation between result keys (`stage.job`, `stage.job#k`) and prompt markers. FE-012 §4.5 asks for a pure `*-view.tsx` where a part can render alone; the diagram, its job cards and the modal compose client leaves and are only ever shown by a client part, so they stay plain `.tsx`. Every handoff is a markdown document drawn by the one generic renderer (`markdown-view.tsx`). The glyphs the visual draws live in `shared/components/core-components/glyphs/`.

## Saved progress

A run (the pasted results and the demo flag) is saved in the browser under the second storage key, `hancrafted:progress` ([FE-001](../../../.archgate/adrs/FE-001-state-management.md) §3). One entry per authored Workflow, `human-in-the-loop/<workflow id>`, carrying `hash`, `demo` and `results`, so every Episode and both languages share one run. The hash is a sha256 of the English and German files together (`hashFor` in `workflow-data.ts`, built at build time by `src/shared/lib/pair-hash.pure.ts`). Reading and writing go only through `src/shared/lib/prefs-storage.ts` (`readProgress`, `writeProgress`, `removeProgress`); the hook `src/shared/hooks/use-progress.ts` loads in an effect, so the static page never depends on storage, and saves on change. A stored entry of another hash never loads: a fresh run starts, saving pauses, and a note offers "Download old progress" or "Discard"; the old entry stays until the viewer chooses. A refused write (quota, private mode) shows a note asking for a download. An uploaded Workflow is not saved. The run model (`workflow-run.pure.ts`) stays the one place that reads results; storage persists its inputs and never forks it.

## Popover steps and the lead

Each numbered step of a stepper item (Provide context, Run the prompt, Check the result) folds by its title (`step-section.client.tsx`). A context field shows its sample as its text until the viewer pastes their own (`shownValue` in `context-entries.pure.ts`), so the earlier result or the scenario is readable where the prompt uses it; a field the viewer empties stays empty and the prompt falls back to the sample. Provide context starts folded while every field holds a value or a sample (`needsInput`). Each step is a box that turns light grey (`bg-muted`) while the pointer is inside it. A job's `goal.review` is authored and checked but not shown in the popover. One control per item leads, filled or framed in the `--info` token colour with `data-lead`: derived from the run, never authored in the Workflow YAML (`nextAction` in `next-action.pure.ts`). The first required step not done leads with its context while a field has neither value nor sample, else its Copy prompt until pressed, then its answer (the result box, or the box to tick); the chat buttons and Copy explanation prompt never lead. Check the result is optional: titled "(optional)", it starts folded and never leads, so a pasted result ends the item, whose number turns into a tick on a green (`--success`) filled circle. Which prompts were copied is transient, held per item while the popover is open.

## Demo mode and Reset

The registry's `demo` control sits after the `</>` toggle inside the toolbar pill, and `reset` sits set apart just after the pill, drawn only once the run has work (`TOOLBAR_ROW`, `TOOLBAR_PILL` in `tool-button.client.tsx`), in the visual's toolbar and in the popover's alike (`demo-controls.client.tsx`). The popover's header holds only the title and Close; its toolbar, under the title, is the same pill: Help, the `</>` toggle, the Demo mode switch, then Reset apart; a Preset hides either with `controls`, and a `readonly` Preset hides both. The parent holds `demo` in its state (default on) and saves it with the run; the switch is disabled once `canChangeDemo` of the run model is false, with the tooltip "Reset to change". Reset takes the `--warning` token colour while a result is pasted (saved work, here or in another Episode), asks to confirm in the page (no browser dialog) with "Download progress" first, then empties the run, turns Demo mode back on and removes this Workflow's entry only (`reset` of `use-progress.ts`).

## Debug mode

The registry's `debug` control is a Debug icon toggle (`debug-toggle.client.tsx`) beside Demo mode, drawn only in development or on a page whose URL carries `?debug`, so a workshop viewer never sees it; its state lives in memory in the parent and is never stored. While it is on, "Copy prompt" and "Copy explanation prompt" append the `debugInstruction` word, which has the AI end every reply with a one-line `[hitl-debug] workflow=… · stage=… · job=… · round=… · prompt=… · step=… · level=… · demo=… · locale=… · source=<short hash>` footer (`debug-footer.pure.ts`) to paste back as feedback; off, the copied text is unchanged.

## Adding a Workflow

A Workflow is one YAML file per language; what is written renders as written. The authoring guide is [agentic-workflow.md](agentic-workflow.md): the schema, markers, slots, repeated stages, handoff templates and every loader problem. Start from `project-plan.en.yml` and `project-plan.de.yml`.

1. Register the pair in `workflow-data.ts` (`FILES`, `WORKFLOW_IDS`). `workflow-pair.test.ts` holds both files to one structure (FE-012 §1.3), and the loader checks every sample and example against its template. The build throws each problem of a shipped file.
2. Viewers may also upload a Workflow file (the same shape, in any language); problems are listed under the toolbar and the authored Workflow stays. A download writes the current file as it is; pasted values are not exported.

Playwright serves the built export at its `baseURL` (design-ADR 0014); the test opens `/explorable-explanations/human-in-the-loop/`.

## Progress file

"Save progress to a file" (toolbar, `progressDownload`) and the "Download progress" notes write one YAML file, `<workflow id>-progress.yml`: `workflow`, `hash`, `demo` and `results`, every result a block scalar so a pasted Markdown result reads as it is (`progressFile` in `src/shared/lib/progress.pure.ts`). "Load progress from a file" (`progressUpload`) reads it back with `readProgressFile`: a file that is no progress file, that names another Workflow, or whose hash is not the shown Workflow's is refused with a message naming the Workflow (`refuse*` words), and the run stays as it was. "Upload your own Workflow" (`upload`) is a separate, second action. An uploaded Workflow has no saved run, no hash to vouch for a file, and so neither progress action; the toolbar shows them only for an authored Workflow. Save shows only once the run has work; Load always shows.
