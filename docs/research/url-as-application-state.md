# URL as application state

Research date: 2026-10-08. Stack at date: Next.js 16.4, React 19.3, `output: 'export'` on GitHub Pages. Scope: terminology for "the URL is the single source of truth for application state", and how that works with Next.js App Router history APIs in a static export. Not binding; binding decisions live in `.archgate/adrs/`. Quotes are verbatim from pages fetched on the research date unless marked. The fetch tool sometimes dropped small words from pages; quotes affected are flagged. Items I could not verify from a primary source are collected under "Unverified" at the end.

## 1. Terminology

### Fielding's dissertation

- **"Application state" is described, never given a one-line definition.** [§5.3.3](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm): "An application's state is therefore defined by its pending requests, the topology of connected components…" (sentence continues with active requests, flow of representations, and how the user agent processes them). Also: "REST concentrates all of the control state into the representations received in response to interactions." and "The application state is controlled and stored by the user agent…". A steady state is reached "whenever it has no outstanding requests"; for a browser that is a web page. §6.3.4.2 ([evaluation chapter](https://ics.uci.edu/~fielding/pubs/dissertation/evaluation.htm)) glosses it parenthetically as "the set of currently rendered representations" on the browser.
- **"Resource state" is not defined as a term.** Nearest text: §5.2.1 "the nature and state of an architecture's data elements is a key aspect of REST"; §5.2.1.1 "a resource R is a temporally varying membership function MR(t)"; §5.2.1.2 representations capture "the current or intended state of that resource" ([ch. 5](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm)). The usual split (resource state lives on the server, application state on the client) is therefore our reading, not a Fielding sentence.
- **"Hypermedia as the engine of application state" is only named, not explained.** §5.1.5 lists it as the fourth interface constraint. §5.3.3 comes closest: the application is "an engine that moves from one state to the next" by "choosing from among the alternative state transitions in the current set of representations." The phrase "engine of application state" does not appear in chapter 6. Source: [ch. 5](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm), [ch. 6](https://ics.uci.edu/~fielding/pubs/dissertation/evaluation.htm).
- **Bookmarks appear once, as an example.** §5.3.3: client-held state lets the user "jump from one application to another (e.g., bookmarks and URI-entry dialogs)." The word "bookmark" is absent from chapter 6, and neither "deep link" nor "bookmarkable" appears.
- **Useful for our framing.** §6.5.4.1 (heading "Application State in a Network-based System"): "The most frequent violations are in regard to the constraints on application state and stateless interaction." §6.3.4.2 uses the "Back" button to argue that state kept outside the rendered representation (cookies) breaks the model ([ch. 6](https://ics.uci.edu/~fielding/pubs/dissertation/evaluation.htm)). Caution: Fielding's "application state" is the whole set of rendered representations, not only the URL. "URL is the application state" is a stronger, web-developer claim than REST makes.

### Deep linking, bookmarkable, shareable

- I found no primary-source definition of "deep link", "bookmarkable state" or "shareable state" in the sources allowed here (Fielding, react.dev, nextjs.org, MDN, WHATWG, angular.dev). Treat them as informal community terms.
- Closest first-party language: Next.js says `next/link` gives SPA-like transitions "with the advantage of persisting application routing state to the URL for linking and sharing" ([SPA guide](https://nextjs.org/docs/app/guides/single-page-applications)). That is a usage statement, not a definition.

### React: single source of truth, derived state, external stores

- **Single source of truth.** react.dev ([Sharing State Between Components](https://react.dev/learn/sharing-state-between-components)): "For each unique piece of state, you will choose the component that 'owns' it. This principle is also known as having a 'single source of truth'. It doesn't mean that all state lives in one place..." Flag: the fetch lost small words here and I restored the sentence from the page's evident wording; re-check against the live page before quoting. The same page notes "even client-side routing libraries are usually implemented by storing the current route in React state". So React's phrase is scoped per piece of state, not app-wide, and it does not mention the URL as a source.
- **Avoid redundant state / calculate during render.** ([Choosing the State Structure](https://react.dev/learn/choosing-the-state-structure)): "Avoid redundant state. If you can calculate some information from the component's props or its existing state variables during rendering, you should not put that information into that component's state." Also "Avoid duplication in state": keep `selectedId`, not the selected object. ([You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect)): "When something can be calculated from the existing props or state, don't put it in state. Instead, calculate it during rendering." Implication: if the URL holds `?tab=notes`, do not mirror it into `useState`; derive the value each render.
- **External store.** ([`useSyncExternalStore`](https://react.dev/reference/react/useSyncExternalStore)): "a React Hook that lets you subscribe to an external store", for "Third-party state management libraries" and "Browser APIs that expose a mutable value and events to subscribe to its changes." React recommends `useState`/`useReducer` "when possible".
- **Does react.dev use a history/location example?** No. The only browser-API example on the reference page is `navigator.onLine` with `online`/`offline` events; "You Might Not Need an Effect" uses the same example. I found no `history` or `location` example on either page. A URL store would be our own application of the hook.
- **Contract points that matter for a URL store** (same page): repeated `getSnapshot` calls must return the same value while the store is unchanged; the snapshot "must be immutable"; `getServerSnapshot` is used "during server rendering and during hydration", must match between server and client, and "If you omit this argument, rendering the component on the server will throw an error."

### State taxonomy (server / URL / persisted client / local UI)

- **No first-party source states the four-way taxonomy.** TanStack Query's docs give the server/client split. The [overview](https://tanstack.com/query/latest/docs/framework/react/overview) says server state is totally different from client state and lists its traits: "Is persisted remotely in a location you may not control or own"; "Requires asynchronous APIs for fetching and updating"; "Implies shared ownership and can be changed by other people without your knowledge"; "Can potentially become 'out of date' in your applications if you're not careful". The [client-state page](https://tanstack.com/query/latest/docs/framework/react/guides/does-this-replace-client-state) calls TanStack Query "a server-state library" and Redux/MobX/Zustand "client-state libraries".
- **Verdict.** "Server state vs client state" is a library-docs convention (TanStack, a non-spec source). Separating URL state and persisted (`localStorage`) state is community convention; I found no spec or framework docs that name those categories. Use the taxonomy as a working vocabulary, not as a standard.

## 2. Next.js App Router (v16) and the History API

### Native `pushState` / `replaceState` and the hooks

- **Documented as supported and integrated.** Next.js SPA guide, "Shallow routing on the client" ([source](https://nextjs.org/docs/app/guides/single-page-applications), v16.4.0, last updated 2026-09-10): "Next.js lets you use the native `window.history.pushState` and `window.history.replaceState` methods to update the browser's history stack without reloading the page." and "The `pushState` and `replaceState` calls integrate into the Next.js Router, allowing you to sync with `usePathname` and `useSearchParams`." The example builds a `URLSearchParams` from `useSearchParams()` and calls `window.history.pushState(null, '', '?' + params)`.
- **Mechanism, from source** ([`app-router.tsx`](https://github.com/vercel/next.js/blob/canary/packages/next/src/client/components/app-router.tsx), canary at fetch time, so line-level detail may drift). The router replaces `window.history.pushState`/`replaceState` inside an effect. A call whose state carries `__NA` or `_N` (the router's own writes) goes straight to the original. Any other call first runs `copyNextJsInternalHistoryState(data)`, then, if a URL was passed, `applyUrlFromHistoryPushReplace(url)`, which resolves it against `window.location.href` and calls `restore(...)`. Cleanup restores the originals. Back/forward is handled by a `popstate` listener calling `traverse(window.location.href, ...)`.
- **Reading side** ([`navigation.ts`](https://github.com/vercel/next.js/blob/canary/packages/next/src/client/components/navigation.ts)): `useSearchParams` reads `SearchParamsContext` and wraps it in `useMemo` into `ReadonlyURLSearchParams`; `usePathname` returns `PathnameContext`. Both come from router state, so a native `pushState` is visible only because of the patch above, not because the hooks read `location`.
- **Gotcha: the router's `useRouter` is the sanctioned writer.** `router.push`/`router.replace` add or replace a history entry ([useRouter](https://nextjs.org/docs/app/api-reference/functions/use-router)). Default behavior scrolls to top; pass `{ scroll: false }` to disable.
- **Not documented: which state object to pass.** The docs example passes `null`. The source copies the router's `__NA` and tree markers into whatever you pass, so custom state objects are tolerated; the docs say nothing more. If a feature stores its own `history.state`, test back/forward.

### Is the hash / fragment exposed by a Next.js hook?

- **No.** `usePathname` "returns a string of the current URL's pathname"; the table shows `/dashboard?v=2` giving `'/dashboard'` ([usePathname](https://nextjs.org/docs/app/api-reference/functions/use-pathname)). `useSearchParams` "lets you read the current URL's **query string**" ([useSearchParams](https://nextjs.org/docs/app/api-reference/functions/use-search-params)). Neither page mentions hash. In `navigation.ts` neither hook touches the hash, and `app-router.tsx` never reads `window.location.hash` (it uses `window.location.href`).
- **Hash-only navigation is acknowledged, but only as a non-event.** `router.bfcacheId` "stays the same for back/forward navigations, `router.refresh()`, and search-param- or hash-only navigations" ([useRouter](https://nextjs.org/docs/app/api-reference/functions/use-router)). So the router does handle hash-only navigations; it just offers no reader for them.
- **Consequence.** To read the hash you must use `window.location.hash` in the browser, from an effect, event handler, or a `useSyncExternalStore` subscription. Prerendered HTML cannot know the hash (it is not sent to the server). The fragment is not in `usePathname` or `useSearchParams` values. MDN: `location.hash` is "a string `#` followed by the fragment identifier", empty string if there is none ([Location.hash](https://developer.mozilla.org/en-US/docs/Web/API/Location/hash); the page text was partly garbled by the fetch).
- **Events.** `pushState()` "never causes a `hashchange` event to be fired, even if the new URL differs from the old URL only in its hash" ([MDN pushState](https://developer.mozilla.org/en-US/docs/Web/API/History/pushState)); `hashchange` "does not fire when the hash is modified using `history.pushState()` or `history.replaceState()`" ([MDN hashchange](https://developer.mozilla.org/en-US/docs/Web/API/Window/hashchange_event)). A store that subscribes only to `hashchange` therefore misses hash changes made through the history API. Next.js issue reports suggest `router.push('#x')` does not fire it either ([#69256](https://github.com/vercel/next.js/issues/69256), reported by a user, not confirmed against source by me). A hash `useSyncExternalStore` must subscribe to both `hashchange` and `popstate`, and (if our own code writes the hash) notify its own listeners after writing. The last point is my inference from the MDN statements, not a documented pattern.

### Static export (`output: 'export'`) and `useSearchParams`

- **`useSearchParams` is allowed, with a Suspense requirement.** ([useSearchParams](https://nextjs.org/docs/app/api-reference/functions/use-search-params), "Prerendering"): "If a route is prerendered, calling `useSearchParams` will cause the Client Component tree up to the closest `Suspense` boundary to be client-side rendered." and "During production builds, a static page that calls `useSearchParams` from a Client Component must be wrapped in a `Suspense` boundary, otherwise the build fails with the Missing Suspense boundary with useSearchParams error." In development "`useSearchParams` doesn't suspend and things may appear to work without `Suspense`", so the failure shows only at `next build`.
- **Practical meaning for a static site.** The query string cannot exist at build time, so the Suspense fallback is the prerendered HTML and the real value appears after hydration. Content that must be indexed or visible without JS should sit outside that boundary. The static-export guide itself does not mention `useSearchParams` ([static exports](https://nextjs.org/docs/app/guides/static-exports)); this conclusion follows from the two pages together.
- **Static export constraints that touch URL state** ([static exports](https://nextjs.org/docs/app/guides/static-exports)): unsupported include Dynamic Routes with `dynamicParams: true` or without `generateStaticParams()`, Rewrites, Redirects, Headers, Proxy, Server Actions, Intercepting Routes, Cookies. So URL state must be client-side only; you cannot rewrite `/de?tab=x` to something else or redirect legacy URLs server-side.
- **Server Components cannot read the URL.** `useSearchParams` and `usePathname` are Client Component hooks; page `searchParams` is a request-time prop, which a static export cannot supply (the guide lists "Route Handlers that rely on Request" as unsupported, and `output: 'export'` generates one HTML file per route). I did not find a page that states outright what the `searchParams` prop contains under `output: 'export'`; treat that as unverified.
- **`usePathname`.** With rewrites or a Proxy, a prerendered page can hydrate-mismatch because the initial value "comes from the server and may not match the actual browser pathname" ([usePathname](https://nextjs.org/docs/app/api-reference/functions/use-pathname)). Static exports on GitHub Pages have no rewrites, so this should not apply, but the project's `basePath` or `trailingSlash` settings were not checked here.
- **React 19.3 `browser()`.** The SPA guide describes `use(browser())` for components whose first browser render cannot match server HTML, with a Suspense fallback as prerendered HTML ([SPA guide](https://nextjs.org/docs/app/guides/single-page-applications)). I did not check react.dev for it, so I cannot confirm the API from React's own docs. Not needed for a `useSyncExternalStore` store with a `getServerSnapshot`.

### Safari / WebKit rate limit on `pushState` / `replaceState`

- **WebKit throws; limit is 100 calls per 10 seconds on the main frame's `History`.** From [`History.cpp`](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/page/History.cpp): `static Seconds stateObjectTimeSpan { 10_s };`, `static unsigned perStateObjectTimeSpanLimit = 100;`, counter `m_currentStateObjectTimeSpanObjectsAdded` reset when the window passes, and a check `>= perStateObjectTimeSpanLimit`. The count lives on the main frame's History object. The error is a SecurityError with text of the form "Attempt to use history.pushState() more than 100 times per 10 seconds" (`replaceState()` gets the same text with its own name). The fetched copy dropped the word "to" from the message, so confirm the exact string. pushState and replaceState share the one counter (same function, `updateAndCheckStateObjectQuota`).
- **Separate size quota.** `defaultTotalStateObjectPayloadLimit = 64 * MB`, throwing a different error (the quota message), not SecurityError.
- **URL checks run first**, then the rate check. SecurityError "Blocked attempt to use history.pushState() to change session history URL from ... to ..." with reasons such as "Protocols, domains, ports, usernames, and passwords must match." and, for `file:` URLs, "Only differences in query and fragment are allowed for file: URLs."
- **Chromium differs.** In Blink [`history.cc`](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/frame/history.cc), when `navigation_rate_limiter().CanProceed()` is false, `StateObjectAdded` just returns: no exception, the call silently does nothing. The numeric limit lives in the rate limiter source, which I did not read. Fetched by a base64 text endpoint; the fetch tool decoded it for me, so line-level quotes are not byte-checked.
- **History of the limit is secondhand.** Developer reports describe iOS 9.3 capping at 100 total, later 100 per 30 seconds, now 100 per 10 seconds ([Apple forum](https://developer.apple.com/forums/thread/36650), [remix-run/history#291](https://github.com/ReactTraining/history/issues/291)). Not confirmed from WebKit commits.
- **MDN says only this.** `pushState()` throws SecurityError "if the method is called too frequently", with no number or window ([MDN pushState](https://developer.mozilla.org/en-US/docs/Web/API/History/pushState)). MDN also notes `pushState` won't load the URL and requires same origin.
- **Design implications (my inference).** Writing the URL on every keystroke, scroll tick, or drag step will trip Safari. Use `replaceState` for transient state, debounce or throttle writes, write on commit events, and wrap calls in `try/catch`. Because Chromium fails silently, the failure appears only in Safari/WebKit, so test there. Next.js's own router writes also count toward the same quota (it calls `pushState`/`replaceState` in `HistoryUpdater`).

## Key facts

1. Fielding defines application state by pending requests, connected components and representations flow (§5.3.3), not as "the URL". Resource state is not a defined term.
2. Bookmark appears once in the dissertation (§5.3.3). "Deep link" does not.
3. React's "single source of truth" is per piece of state, and derived values should be calculated during render, not stored.
4. react.dev's `useSyncExternalStore` browser example is `navigator.onLine`; no history/location example exists.
5. The server/URL/persisted/local taxonomy is community convention. Only server vs client has first-party docs (TanStack).
6. Next.js 16.4 documents native `pushState`/`replaceState` as integrated with `usePathname` and `useSearchParams`.
7. No Next.js hook exposes the hash; read `window.location.hash` on the client. Angular exposes `ActivatedRoute.fragment`.
8. `pushState`/`replaceState` never fire `hashchange`.
9. `useSearchParams` in a statically exported page needs a Suspense boundary or `next build` fails; the query value only exists after hydration.
10. WebKit throws SecurityError after 100 history writes per 10 seconds; Blink silently ignores writes past its limit.
