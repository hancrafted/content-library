# Resources overview

Amended by #404: a Resource becomes every public, listed item, the Template record kind replaces the old Resource record kind, and Explorable pages move to `/explorables/`. See `docs/features/explorables/README.md` and `docs/features/resources.md`; where they differ from the decisions below, they win. The record kind is now Template (#412): read "Resource" below as Template, `TEMPLATE_TYPES` (`episode-template`, `master-slide`), `templates/` folders, `TEMPLATE_SLUGS`, and the page reference kind `template`; `/resources/` and its overview stay.

The four authoring pages (the Episode template, the Workshop template, the Slide library and the Explorable explanations page) sat under `/episodes/` as tooling pages: `noindex`, out of the sitemap, reachable only from links under the Episode browser. They are content a visitor should find: the interactive explanations bring visitors back (horizon 2), and the templates and Master slides show what the library is made of. They are not Episodes, so they cannot live in the Episode overview. This record gives them a header nav item, an overview and a page each, and retires the tooling page from _Content data model_.

Settled with Han in a grilling session on 2026-10-27. The Archgate amendments it needed (FE-002, FE-004, FE-007, FE-008) were made by Han. The model changes are amendments to _Content data model_ and _Source tree follows the product_.

## Decisions

1. **A Resource is a public page that is not an Episode.** It is one of three types, a closed `TEMPLATE_TYPES`: `explorable-explanation`, `episode-template` and `master-slide`. A header nav item, "Resources" ("Ressourcen"), leads to `/resources/`, a plain `NavLink` between Events and the dashboard, no dropdown.
2. **The overview `/resources/` is a page-assembly template** on `PAGE_CONTAINER`, `src/page-assembly/resources-overview/`. It follows the Events overview: a card grid by default, a list on request (transient state, FE-001 §1), a search over title, description and Tag names, Tag chips and a type filter ("Explorable explanations", "Episode templates", "Master slides"). It reuses the shared search and chip controls and builds no generic filterable browser. The first cut is a plain list of cards linking to each page; the grid, search and filters follow.
3. **The record is `src/content-store/templates/<slug>.ts`**: `slug`, `type`, `tags` (a tuple, lead first) and `visibility`. Its route is worked out from the type and slug, `/<type plural>/<slug>/`, and never stored, so the record and the URL rule cannot disagree. The title, caption and description are the words of the Resource's composition, in its own `i18n/` pair keyed by the folder's slug (FE-003 §4: an Episode's words ride on its record, and a Resource is composed like one); the record holds no text and no second copy exists.
4. **URLs are `/<type plural>/<slug>/`, all public, indexed and in the sitemap**, in both locales:

   | Resource          | URL                                           |
   | ----------------- | --------------------------------------------- |
   | Context window    | `/explorable-explanations/context-window/`    |
   | Human in the loop | `/explorable-explanations/human-in-the-loop/` |
   | Episode template  | `/episode-templates/episode-template/`        |
   | Workshop template | `/episode-templates/workshop-template/`       |
   | Timelines         | `/master-slides/timelines/`                   |
   | Grids             | `/master-slides/grids/`                       |

   Every route closes its params (FE-005 §1), one route per type, and the page catalogue lists every Resource page, so the post-build test expects them. The page reference kinds are `resources` and `resource` (FE-008 §1.3); `resource` carries its type and its composition's ref.

5. **Old URLs redirect with 301** in `public/_redirects`, both locales (FE-005 forbids `next.config.ts` redirects): `/episodes/explorable-explanations/*` and `/episodes/slide-master/*` to `/resources/`, which each split into two pages, and `/episodes/episode-template/*` and `/episodes/workshop-template/*` to their new pages. The old anchors were never published, so nothing a link names breaks.
6. **A Resource is not an Episode.** Its page is an `episode()` composition, so it gets the table of contents and the Context drawer through the one container (FE-002 §1), but it never appears in the Episode ids, the Episode browser, Featured or a Playlist. It is served by a page-assembly template, `src/page-assembly/template/`, which hands the container the route its type gives.
7. **Folders follow the Resource.** `src/episodes/tooling/` becomes `src/episodes/templates/`, one folder per Resource, and `TOOLING_SLUGS` becomes `TEMPLATE_SLUGS`, generated by `npm run registry`. The Explorable explanations page splits into `context-window/` and `human-in-the-loop/`; the Slide master splits along its two Sections into `timelines/` and `grids/`, and every Slide folder keeps its slug. Each composition is a Title slide and its Section. A Resource page is a page-assembly template composing Slides, so `src/explorables/` stays components only (_Source tree follows the product_ decision 4).
8. **An Explorable explanation page shows one Slide per Preset.** A Title slide first, then each Preset with its own readme on the Slide: what it shows and which controls to try. "Every part and control" (`gallery-full`) is one of the Context window's Slides.
9. **All six are public and indexed**, the two Episode templates and both Master slide pages included. Each has a description that says what it is for.
10. **The store refuses a mismatch.** A Resource whose composition folder does not exist, and a composition folder without a Resource record, both stop the load with a sentence naming the Resource (FE-013 §3). The generated record registry is typed against `TEMPLATE_SLUGS`, so `tsc` stops it first.

## Considered options

- **`/ressources/` as the German spelling of the path.** Rejected: one logical path per page, localized by the `/de` prefix as every other route (FE-003 §1); a translated path would need a second route tree.
- **`/resources/<slug>/` flat URLs.** Rejected: the type in the path says what a visitor is opening, and each type can grow its own overview later.
- **An Explorable explanation as an Episode with `format: 'explorable'`.** Rejected: it would enter the Episode ids, the browser, Featured and Playlists, and every list would need a rule to hide it; a Resource has no Video, no status and no release date.
- **Keeping `tooling/`.** Rejected: the folder named the pages for what they were to the authors; it now names what they are to a visitor, and an agent looking for "where is a Resource" finds `resources/`.
- **`page-template` and `shared-slides` as type names.** Rejected: `page-template` is the old name of the Episode template, and Slides are not shared (vision rule 4); the three types name what a visitor gets.
- **One `slide-master` Resource.** Rejected: its two Sections are two catalogues with two audiences, and a page of twenty Slides cannot be linked as one thing; Timelines and Grids each get a page and a description.
- **Title and description as Translation keys on the Resource's own owner.** Rejected: the composition already holds them by slug in its own `i18n/`, and a second pair would state the words twice.

## Consequences

- A new Resource is one composition folder, one record file and `npm run registry`; its page, route, sitemap entry and static params follow.
- Resource pages are public: their placeholder words are read by search engines, so each description says what the Resource is for.
- The Episode overview keeps one link to the Resources under its grid.
- UX taste here is held by review only, the product vision's known gap: the overview's layout and filters have no automated check.
