# Software ecology flow model and use-case files

The software ecology Explorable (`src/explorables/software-ecology/`) shows an organization as a factory. The Customer's requests come in, conveyor belts carry documents between work centers, work waits in each center's backlog, inspection is the review, and releases go back to the Customer. Each role is a work center with two dials, efficiency (how much it puts out) and effectiveness (how likely a handoff is good). AI raises a work center's output and leaves its quality alone. Every queue, rework loop and shipment comes from one model fed by one data file per use case. A new use case is therefore data, and the numbers on a card always match the picture. The product design (concept, use cases, interaction, visuals) is in [the feature guide](../features/explorables/software-ecology.md); this record binds the contract every use case is written against.

## Decision

### Model

1. **One seeded, time-stepped queueing network behind a small interface.** `factory-model.pure.ts` is an open queueing network, `createFactory(useCase, settings, seed)` returning `step(weeks)`, `set(settings)` and `read()`, whose Snapshot gives each work center's backlog, weeks of work waiting, rush, busy share and work in progress, the documents in transit per belt and the Customer's readouts. The traffic solve, the sizing and the stability check live inside it and surface only as the Snapshot's headroom and as refusals at load. It knows who hands work to whom, never where anything is drawn. It is advanced in fixed steps from a fixed seed, with separate random streams for arrivals, service and routing, so toggling one setting leaves the others' draws unchanged. A job finishes at a float time within a step, so capacity stays exact at any efficiency. Time runs on a real-time accumulator; speed is weeks per second (1×, 2×, 5× default, 10×), with a cap on steps per frame. Presets warm up 60 weeks in chunks across frames; Clear starts empty at day 0, and a clock reads "Day n" in working days. Every handoff takes a fixed quarter of a working day whatever the belt's length, so a belt never acts as a hidden queue. The renderer reads the Snapshot; it never feeds the model. The model lives in the Explorable's folder until a second user needs it.
2. **A node is a work center, one per role.** Each has a capacity in jobs per week and service times drawn from a normal distribution (CV 0.3) or, where the file says so, an exponential one; Ideal uses steady service. People are optional clusters of node ids; a person serves the center with the most waiting work. One Customer node is both source and sink. It sends requests at a rate, Steady (one every 1/λ) or Random (Poisson), split by a configurable mix (new customers to sales, feature and change requests to the product manager, bugs and support tickets to support), and receives what operations releases. In Product company mode, a use case's own sources (e.g. the product manager's roadmap, sales leads, engineering's tech debt) also create work inside the factory, sharing the same backlogs first in, first out; Service provider mode has the Customer as the only source. The Customer counts customer requests fulfilled and own roadmap shipped apart. Each release may at once trigger a new request with a chance set per good and per bad release; a bad release's request is the customer complaint. The total of these follow-up chances stays below 1, which the stability check covers.
3. **Two dials per work center, plus fan-out.**
   - **Efficiency** (10 % to 1000 %, a log slider) sets the work center's speed, so raising it pushes more work downstream and moves the bottleneck there.
   - **Effectiveness** sets the chance that a handoff is good or bad.
   - **Tasks handed on per task (fan-out)** sets how many documents one input becomes (one spec, five documentation pages); each document is a task for the next work center, and only a request's main document counts as fulfilled.
   - Each setting shows its set value beside its effective one, e.g. "100 % → 250 % with AI".
   - A handoff's quality is the worse of what came in and the work center's own result. A work center with more than a week of work waiting rushes: its effectiveness drops, by up to 15 points.
4. **Backlogs are unlimited; stability is checked.** A work center's backlog is a ticket backlog with no limit, stored as runs of identical jobs; belts carry only documents in transit. An optional `buffer:` blocks the sender after service, for a real physical limit. At load, the traffic equations are solved at the Realistic dials, rework, churn and complaint flows included, and every center is sized for that load; a use-case file is refused when a center would need more than 1.5× its Ideal capacity to cope (a person's: the sum), since its Realistic dials are then unrealistic. Ideal runs every center at about 70 % load; Realistic is busy but coping, its named bottleneck near 90 %; overload, a backlog that grows without end, comes from AI or a pushed dial.
5. **Bad work does damage downstream.** Each mechanic has a strength in the use-case file and a visible sign:
   - **rework:** a bad input is sent back to the sender, to the front of its backlog, with a probability; it rides back on a return belt.
   - **churn:** a bad input that is kept multiplies the receiving work center's fan-out (follow-up questions, patches).
   - **extra work:** a bad input takes the receiving work center longer.
   - **customer complaints:** a bad release triggers a bug or support request from the Customer, marked as a complaint, which adds work to the system; a bug it hands to engineering jumps to the front of engineering's backlog.
   - **passing unread:** every inspection passes more bad work unflagged as its queue fills (`stampUnderPressure`, no toggle).
     Isolating work centers, following an order and taking a work center out are removed; an overlay seam keeps the first two easy to bring back.
6. **AI raises output and leaves quality alone.** Per work center, AI has two settings: a speed-up (1× to 5×, 2.5× by default) and extra tasks per task (1× by default), which also scales a role's own tickets in Product company mode. Presets set both, so AI everywhere at Ideal keeps output at 1.0× with a shorter lead time, while AI at one role alone floods the next one. Effectiveness stays as it was (Brief Constraint: AI is an accelerator, never a solution). An "AI quality effect" setting in the model, default `same`, lets a scenario show AI improving or worsening quality, so the model never implies that AI cannot raise quality.
7. **Readouts are bands, not counts.** Output counts fulfilled requests only, never the extra documents of churn or rework, relative to Ideal ("1.8× ideal"); a backlog reads as weeks of work waiting, amber from one week and red from two; the stage reads "Illustrative model, not measured". Queueing measures (utilisation busy, starved and blocked; throughput; average backlog; lead time by Little's law, shown only while the backlog is steady) sit in a collapsed "How it flows" section in plain words. The constants are tuned to tell the story; nobody measured them.

### Files

8. **One use-case file and its locale pair.** `<use-case>.yml` holds the master data: the Customer (rate, arrivals, request mix, follow-up chances per good and bad release), work centers (`role`, position hints, enabled dials and their defaults, service distribution, optional `buffer`, and `spawns`: what a finished job creates downstream, as `{ to, n }`, `{ to, p }` or `choose: [{ to, w }]`, from which the belts are derived), damage strengths, AI profile overrides and `presets`. `<use-case>.words.yml` and `<use-case>.words.de.yml` hold every word keyed by id ([FE-012-explorables](../../.archgate/adrs/FE-012-explorables.md) §1: same keys, words differ).
9. **A shared role catalog.** `roles.yml` and its words pair give each role its classic artefacts, its execution tasks and its AI examples, e.g. sales turns leads into deals and requirements for the product manager and analyst. A use case names a role by id and overrides only what differs.
10. **Presets are one ordered row of states.** `presets: [{ id, view, reality, dials?, ai?, compare? }]` render in order as the toolbar's state row. `view` is `swing`, `roles` or `factory`. `compare` lists up to three work centers and opens the compare stream. Every use case ships Ideal, Realistic, AI unbalanced (AI where one role would adopt it alone, e.g. engineering at 2× extra tasks: fewer requests fulfilled, the next work center overloaded) and AI balanced (AI where needed, capacities matched and demand raised: 2–3× ideal output at about 92–97 % satisfied with Realistic effectiveness), tests pinning both AI bands. The toolbar shows Swing, Roles, Ideal and Realistic, and a Scenarios menu holds the rest. Each scenario has a one-line "what to watch" caption; Tire swing's scenarios also have guided tours of three to five steps, each setting dials, running to a week and pausing with a caption pointing at a card. A scenario step carries `expect:` claims on the model's readouts (e.g. `qa.weeksWaiting: ">2"`), so the tour and its check are one source.
11. **Download and Upload exchange one file.** Download writes the current state as one YAML with every language at its root, `i18n: { en: {…}, de: {…} }`. `use-case-file.ts` is the only module that reads YAML, the shipped pair and the exchange file alike, and returns a typed use case or its refusals. Upload validates such a file with the zod schema, splits it in the browser and loads it. The shipped source stays the use-case file plus its locale pair, picked at build time, so FE-012-explorables §1 holds; the exchange file is runtime data a visitor brings. Upload ships in v1 with an issue tracking its validation errors.
12. **Checks.** A zod schema test per use-case file and for the exchange format, the FE-012-explorables pair test per words pair, and the build throws on any broken shipped file. `factory-model.pure.test.ts` holds characterisation cases per use case: Ideal ships only good work; every load stays below capacity at Realistic; Realistic stays stable over seeds (batch means); after a congestion, Ideal drains to under a week of work; raising the bottleneck's efficiency moves the bottleneck downstream; work is conserved across a dial change; the two AI presets hold their bands; every `expect:` of every scenario step holds on the model alone, with a fixed seed and no rendering, run by `factory-scenario.pure.ts`, which the tour uses as well; the same seed and inputs give the same state.

### Rendering

13. **One card component with four views.** `WorkCenterCard` takes `cardView: swing | role | station | dashboard`.
    - **Swing and Roles:** every card at its factory position, with no belts; the cartoon panels without a work center fill the empty cells.
    - **Factory:** the same positions as stations; switching views only fades panels and belts in or out.
    - **Dashboard:** status, dials, the role's artefacts and tasks, and what AI does there.
      The name is not `renderMode`, which FE-012-explorables §4.3 reserves for Simple and Technical.
14. **One stage, two layers.** One stage component renders everything from the model, the layout and the view, and reports a click on a card back up. Its work centers, belts, cards and labels are DOM/SVG, labelled and keyboard reachable; the documents on the belts and the pile-ups are one canvas, drawn every frame outside React. One `useFactory` hook is the only bridge between the model and React: it holds the model, runs the frame loop and hands the parent a readouts slice a few times a second. The renderer keeps its own screen time, so handoff and slide-in animation never reach the model; its one seam is the pile style (heap, leaning stack, drift). The flow holds 60fps under any dials: transit objects are pooled, drawn documents are capped and merge by their marks into one with a "×n" badge, icons come from a pre-rendered sheet, and the DOM is written only on change, readouts at a few hertz. It pauses off-screen and shows one steady frame under reduced motion. Inside a station a rack of six slots on the left holds the waiting work (past six, the top slot turns red with "+n" beside it, and the surplus piles up at the end of the incoming belt, growing with weeks of work waiting and drawn differently per station), and the document in work in the middle, at twice the slot size, fills, in the `ai` tint where AI is on, and is stamped good or bad. A document slides from the belt into the rack and from the rack to the work position, and a finished one shrinks as it moves out onto the belt: nothing appears or vanishes abruptly. A handoff is drawn over a fixed 0.6 s of screen time at any speed, while the model counts a quarter day. Belt motion can be switched off.
15. **Document icons show quality and origin.** A plain document is good; a red minus marks bad, a red warning marks a complaint or rework, and an AI-made document has an orange border, a light orange fill and a star; the marks combine. Fan-out leaves as separate documents. AI is drawn as a turbo on the belt.
16. **The Customer shows output beside outcome.** A 3×4 grid of the last twelve releases, each good or bad with complaints marked, gives the customer satisfaction rate under it; output relative to ideal sits beside it, so more output next to a redder grid reads at once.
17. **Selection and compare.**
    - **One work center:** clicking it opens its dashboard as a popover anchored to it, which closes on a second click, × or Esc. The dashboard is a monitor: a traffic light, signals (keeping up, bottleneck, starved, overloaded, rework-heavy, passing unread) and trend charts of output, outcome and queue; only the AI toggle sits on it, and the dials are in a collapsed Settings section.
    - **Compare mode** (a toolbar toggle, or shift-click): select up to three work centers. The Compare button flattens them into a three-column stream, with the station view above the dashboard view in each column, a "+n stations" gap for skipped ones, an overview strip, and Exit to return.
    - Belts between neighbouring columns carry the live flow.
    - The parent owns the selection, the compare set and the help toggle; each part gets its slice and callbacks (FE-012-explorables §4).
18. **Progressive disclosure.** At rest only belts, work centers and documents show. Queue trays, counts and damage signs appear under pressure, with a gap between showing and hiding so they never flicker, or on hover and focus. Help text shows on every card while the shared help toggle is on; otherwise controls carry tooltips.
19. **Layout is data plus computation.** The use-case file gives position hints; `factory-layout.pure.ts`, apart from the model, keeps a minimum belt before and after every station and places the work centers in rows on a stage that fills the viewport below a sticky toolbar, scaled down on narrow screens, and the compare stream is a computed linear layout.

## Alternatives and cost

- **A `FlowRenderer` seam** (round 6's version) had one adapter, the canvas, so it was a hypothetical seam; the pile style, with three, is the real one.
- **A pure `advance(state, dt)` returning a new state** allocates every step and breaks the pooled buffers that hold 60fps.
- **One canvas for everything, cards included,** gives up screen readers, the keyboard and the card's reuse as the dashboard popover.
- **The plumbing analogy** (this record's first version) had nothing that read as rework or extra work, and in the prototype its dotted water read as clutter. Han knows those mechanics from manufacturing.
- **A steady-state model** (the first version) gave defined numbers, but a faster upstream work center simply idled, so the dials changed nothing visible.
- **Bounded queues sized for balance** (round 4): belts stored the overflow without limit, Messy never settled and recovery took about 150 simulated weeks.
- **A loop-gain check alone:** fan-out and churn amplify work without forming a loop, so a use case can pass it and still overload every center downstream.
- **A true discrete-event engine** gives the same results at this scale but loses the fixed-step, same-seed, same-picture guarantee.
- **Words inside the shipped use-case file** under `i18n:` would break FE-012-explorables §1 and ship German into every English page; only the exchange file carries them.
- **Damage mechanics as prototype switches** would hide the very effects Han wants managers to see.

The cost:

- The time-stepped model needs its seed, warm-up and characterisation tests to stay presentable.
- Upload adds a validation surface.
- The Brief's Analogy and the Dossier's spoken words are rewritten in the factory vocabulary.
