# Episode design is reviewed as a static HTML Spec

Han reviewed an Episode's design as a markdown build spec and a markdown design spec whose visuals were ASCII wireframes inside prose. That was slow to read, so the design got approved unread, and visual problems surfaced only after Build, where a redo costs a Section Job and a dev server. The Specification Stage now writes one Spec, a static HTML page that shows every Slide as two or three true-alternative Options, which Han picks from in a native form. From its Gate on, the Spec is the Episode's only source. Issue [#209](https://github.com/hancrafted/content-library/issues/209).

## Decisions

1. **One static page.** `write-spec` writes `docs/episodes/<slug>/spec/spec.html`, fully self-contained: the CSS compiled from the site's `globals.css` is inlined as `<style data-design-css>` by `spec-assemble`, so the page needs no sibling file, script or link. It replaces `spec/spec.md` and `spec/design-spec.md` (amends design-ADR-0008 §5). It opens with a JSON meta block (the frontmatter equivalent), the Brief's Style, the Visual language and an Episode page section, then the Title-slide article, then one section per Section and one per Slide, slugged as the Dossier headings. Each Slide carries its title, then its Visual idea, Voice script and Speaker notes with citations in full as CSS-only tabs (one panel open, every panel in print), then its Options below them.
2. **Two or three true-alternative Options per Slide, at low to medium fidelity.** Options differ in layout, visual metaphor or chart type, never only in colour, spacing or copy. Each has a visible id (`3b`), a reason, a build cost and build notes, and exactly one per Slide is recommended. Options settle the on-screen title, layout, visual components, shapes, graphs and charts, and the hard UI calls (hierarchy, density, emphasis). They are shown at desktop width, light theme and English only, with token classes only. A mock shows the shared Slide header and uses the shared hover classes live where hover helps Han present, so he reviews hover in the preview, and a Context marker beside each fact whose Speaker note carries a source, naming the note it opens; entrance motion is the Slide wrapper's, so no Option specifies it, and a `motion:` note covers purposeful emphasis or hover alone. Dark mode, mobile, German, final body copy and exact spacing are left to Build.
3. **Review through a native form saved as a feedback round.** Per Slide Han ticks zero, one or several Options and dictates a note; a note is required when nothing is ticked. A small Spec server serves the page outside `src/` and the static export, and its form POST writes the next `feedback/<NN>/feedback.md`, in the PR loop's feedback format with `via: spec`. One feedback format serves both reviews and the style harvest.
4. **The Gate loops until every Slide has one pick.** A Slide with exactly one pick is locked. Slides with zero or several picks get a new `write-spec` Attempt that designs fresh Options from the note, for those Slides only. When every Slide has one pick, Han approves the Spec with `approve.ts`, which appends to the meta block's `verified` list.
5. **The Dossier is deleted at the Spec Gate.** The `Gate: approved spec` commit deletes `dossier.md`, so no second truth remains. The Voice script is written before the Spec, as designer context, and loses its own Gate: Han reworks it against the built Slides.
6. **After the Gate the Spec is the only source.** Build reads it alone. PR-loop changes, Voice script changes included, land in the Spec first, then in the implementation (amends design-ADR-0004 §1).
7. **Promotion files the Spec's Options into the Design archive.** The words already live in each Slide's `i18n/`, so none move; every Option, with its feedback and designer prompts, lives on in `design-archive/<slug>/`, and the Spec is deleted with Staging (design-ADR-0004 §2, and settles design-ADR-0008's open question on `spec/`).
8. **The Title slide is reviewed as Hero motif sets.** The Title-slide article carries three Options, each a **Hero motif** drawn from the Red thread and shown as a set: the Title slide's mock and, under it, one section slide per Section that echoes the motif and brings in its Section. Han judges the motif across the Episode in the same review round, and picking an Option picks the set. Build makes the picked set the Episode record's `title` Slide and the section slides' Scenes. Feedback after the Gate keys the Title slide as `top` and a section slide by its Section slug.
9. **Governance moves from markdown-harness to a contract test plus a rubric.** The markdown-harness rules for the two spec files are removed. A pure Spec check, run from the staging-folder check in `npm run verify`, enforces the page's structure: Slides and slugs, the Title slide with its three sets, Option count and recommendation, captions and build notes, Voice script items, resolving citations, no hex colours or arbitrary Tailwind values, the meta block, one pick per Slide once approved, no Dossier beside an approved Spec. The `write-spec` rubric carries the judgement: true alternatives, the Visual language, FE-007, FE-009 and FE-011.

## Amendment: the Spec is assembled by script, from the Brief gate on

Issue [#219](https://github.com/hancrafted/content-library/issues/219). The Spec exists from the Brief gate and grows by stage: the Brief gives Slide cards with purpose and visual idea, the Dossier adds the Voice script and Speaker notes, the designers' fragments add the Options. `episode:spec-assemble <slug>` builds the page through the pure `assembleSpec(inputs)` in `src/pipeline/lib/episode-spec-assemble.pure.ts`; agents supply only content (the designers' fragments, the Visual language and Episode page markup) and never write the page by hand. The script owns the head, outline, masthead, Section bands, the Title-slide article with its echoes, word tabs, meta block, pick boxes, note fields, review form and the `data-picked` and `checked` locks of every feedback round (a Slide's latest round with exactly one pick locks it). It runs the Spec contract once Options exist and refuses once the Spec is approved. This replaces the orchestrator's hand-assembly of decision 1's page.

## Amendment: the Spec template is authored by to-decision-html

Issues [#556](https://github.com/hancrafted/content-library/issues/556) and [#562](https://github.com/hancrafted/content-library/issues/562). The page frame had grown past what the assembler's string template could hold: the skill `to-decision-html` carries the layout, pick-target, device-toolbar and feedback lessons, and the Spec passed them by. The work now splits in two.

- **The skill authors the template.** `skills/new-episode/assets/spec-template.html` is a page frame plus two `<template>` elements, an item and an Option, with named slots. It meets the skill's page contract. Everything Episode-specific the skill needs sits in one file, the Spec calibration `skills/new-episode/references/spec-calibration.md`: the mode, fidelity and design size, the render presets, the slots, the assembler's attributes, the save API and the Next actions. The skill stays free of Episode knowledge, and the template is regenerated when the skill or the calibration changes, never per round.
- **The assembler fills it.** Each round `assembleSpec` clones the two `<template>`s and fills their slots from the designers' fragments, which keep their format. The attributes it sets are in the calibration. It emits `data-recommended` as `"true"` or `"false"`, the form the skill's page contract reads, where the fragment carries a bare attribute: the fragment's format is unchanged, the page's is not. Locks, `data-picked` and the earlier rounds work as before. The outline, intro cards and Section bands stay assembler markup; the intro cards are one row of collapsibles, closed by default, so the first Slide starts high on the page.
- **The feedback format is the Spec's own.** The form posts to the local Spec server, which writes the round's `feedback.md` in the existing line format plus a `page` line and a `next` line (calibration, "Saving the review"). `approve` needs exactly one pick on every Slide, which the page and the server both enforce. The skill's download and copy routes are not used.
- **The review asset is gone.** The form is part of the template, so the check that a Spec inlines `spec-review.html` and the file itself are removed. A Spec assembled before this change keeps its inlined form and stays valid, since the contract reads the fields a page posts and no longer a copy of the form.
- **The `write-spec` job reads the Spec calibration** instead of the old frame and review asset; the Spec Gate pipeline check asserts it.

## Considered options

- **Render a view of the Dossier as the review page**, keeping the Dossier the source. Rejected: the Options and their picks have no home in the Dossier, and a rendered view of one file next to two spec files keeps three truths alive.
- **Let the Spec coexist with the build spec and design spec as tickets.** Rejected: Build would read three files that can disagree, which is what the single source is meant to end.
- **Free-form HTML per Episode.** Rejected: designers would each invent a review form, and a reviewer agent could not check structure. One shared Spec template and a contract test make every Episode's page behave the same.
- **Save the review by clipboard or the File System Access API.** Rejected: the clipboard needs a paste step that loses work, and File System Access is Chromium-only and asks for a folder each time. A native form posted to a local server writes the round with no copy and paste.
- **Promote the Spec whole** into the code folder. Rejected: a Slide is a self-contained folder (design-ADR-0001), and an Episode-wide Spec would claim text that a Slide copied into another Episode also carries. The Slide's `i18n/` stays the one owner of its words; the Design archive keeps the Options as a record, not a source.

## Agent-decided (contest in review)

- The Spec check is `checkSpec(files, stage)` in `src/pipeline/lib/episode-spec.pure.ts`; `checkStagingFolder(files, known)` runs it.
- The page's markup is addressed by role, never by styling class: `data-spec` on `section`, `title-slide`, `slide`, `option`, `mock`, `echoes`, `echo`, `build-notes`, `voice-script`, `speaker-notes`, `visual-idea` and `context-marker`, plus `data-number`, `data-option`, `data-section`, `data-recommended`, `data-picked`, `data-source` and `data-note`, which names the Speaker note a Context marker opens by its title. The Title-slide article is `id="top"`, its Options `0a` to `0c`, its fields `pick:top` and `note:top`. The meta block is `<script type="application/json" id="spec-meta">`.
- The review form lives in the Spec template (see the amendment on the template above). The per-Slide fields sit beside what they review and join the form by `form="spec-review"`: a checkbox `pick:<slide-slug>` valued by the Option id, a note `note:<slide-slug>` per Slide and one `note:visual-language`, and the form itself holds the general comment `note:page` and the Next action `next`. A `data-picked` Option's checkbox, and no other, carries `checked`, so a locked Slide arrives ticked in the next round and the save needs nothing on it.
- A Slide's words (Visual idea, Voice script, Speaker notes) are `<details>` collapsibles in the item's rail, closed by default and outside the review form, so they need no script and never post.
- The sample Spec carries an inline fallback stylesheet in a CSS layer declared before the inlined design CSS, so it reads in system colours when the compiled tokens are missing.

## Consequences

- Han's reviews per Episode become three: the Brief, the Spec and the PR loop. `customize-pipeline` keeps its Gate for a few more Runs.
- The pipeline template drops `write-design-spec`, and `write-voice-script` loses `gate: human`. Per-run pipelines already approved keep their own `pipeline.yml`.
- **Brief** and **Spine** are kept in step with the Dossier until the Spec Gate and with the Spec after it.
